## Issues Found

### Issue #1: VERIFICATION_GUIDE.md Doesn't Claim Authority

**Severity:** **MEDIUM**  
**File:** `docs/VERIFICATION_GUIDE.md`  
**Line:** 1

**Current State:**
- Document explains backend verification requirements
- Referenced as "Server-Side Verification" in README
- No explicit claim to be authoritative for backend responsibilities
- Could be interpreted as "one of many guides" rather than "the guide"

**Risk:**
- Users might look for other verification guides
- Could create confusion if multiple verification documents exist
- Weakens the "single source of truth" principle

**Recommended Fix:**

Add to top of `VERIFICATION_GUIDE.md`:

```markdown
# App Attest Verification Guide

**This is the authoritative guide for backend verification responsibilities.**  
This document defines what must be verified server-side beyond decoding. The decoder provides inspection; this guide defines verification.

**Scope:** Backend/server-side verification requirements.  
**Status:** Authoritative for verification scope and requirements.
```

**Rationale:** Explicitly establishes authority for backend verification scope, matching the pattern used in frontend contract.

### Issue #2: Soft Language in E2E Contract Weakens Boundaries

**Severity:** **MEDIUM**  
**File:** `docs/APP_ATTEST_E2E_CONTRACT.md`  
**Lines:** 42, 54, 80

**Current Language:**
- Line 42: "Backend **should** persist `keyID → publicKey`"
- Line 54: "Backend **should** log it and store on the flow"
- Line 80: "Backend **should** emit the same six values"

**Security Impact:**
- "Should" implies optional, not mandatory
- Could be interpreted as "nice to have" rather than "required for correctness"
- Weakens enforcement boundaries

**Recommended Fix:**

```markdown
- **Rule:** Backend **must** persist `keyID → publicKey` (e.g. on disk) or clearly document that restart requires re-register. If persistence is not implemented, frontend must re-register after backend restart.

- **verifyRunID:** Generated by frontend at the start of each client-data-hash request. Backend **must** log it and store on the flow. One grep reconstructs the full chain.

Backend **must** emit the same six values as the frontend, keyed by flowID and verifyRunID:
```

**Rationale:** "Must" establishes mandatory requirements. If something is truly optional, it should be explicitly marked as such.

### Issue #3: Duplicate Frontend Scope Explanations

**Severity:** **MEDIUM**  
**Files:** 
- `docs/APP_ATTEST_E2E_CONTRACT.md` (line 103)
- `docs/ios_test_app/README.md` (lines 3-5)
- `README.md` (line 113)

**Current State:**
All three documents explain that the iOS test app is "reference only" / "not production" / "diagnostic only", but with slightly different wording:

- `APP_ATTEST_E2E_CONTRACT.md`: "reference frontend only—not a production client; intentionally verbose, forensic, and non-optimized"
- `ios_test_app/README.md`: "diagnostic iOS test application... does not define production frontend behavior"
- `README.md`: "reference frontend only—not a production client"

**Risk:**
- Wording could drift over time
- Inconsistencies could confuse readers
- Multiple sources of truth for same concept

**Recommended Fix:**

**Option A (Preferred):** Make `ios_test_app/README.md` the authoritative source for test app scope, reference it from others:

In `APP_ATTEST_E2E_CONTRACT.md` line 103:
```markdown
The iOS test app is a **reference frontend only**—not a production client. See `docs/ios_test_app/README.md` for complete scope definition.
```

In `README.md` line 113:
```markdown
The in-repo iOS target is a **reference frontend only**—not a production client. See `docs/ios_test_app/README.md` for complete scope definition.
```

**Option B:** Keep current wording but add cross-reference to prevent drift:
```markdown
> **Scope:** See `docs/ios_test_app/README.md` for authoritative scope definition.
```

**Rationale:** Establishes single source of truth for test app scope, prevents wording drift.

### Issue #4: Frontend Contract References E2E Contract Without Hierarchy Clarification

**Severity:** **LOW**  
**File:** `docs/ios_test_app/FRONTEND_APP_ATTEST_RESPONSIBILITY_CONTRACT.md`  
**Line:** 409

**Current State:**
```markdown
**References (for context only):**
- **`../APP_ATTEST_E2E_CONTRACT.md`** - E2E protocol contract (test app + backend)
```

**Risk:**
- Both documents define aspects of frontend behavior
- E2E contract defines "what frontend sends" (line 46-56)
- Frontend contract defines "what frontend is allowed to do"
- Could create confusion about which takes precedence

**Analysis:**
- E2E contract defines **protocol** (what data is sent, flow)
- Frontend contract defines **behavior** (what frontend can/cannot do)
- These are complementary, not conflicting
- Current wording "for context only" is appropriate

**Recommended Fix:**

Clarify the relationship:

```markdown
**References (for context only):**
- **`../APP_ATTEST_E2E_CONTRACT.md`** - E2E protocol contract (test app + backend)
  - Defines protocol (what data is sent, flow sequence)
  - This contract defines behavior (what frontend is allowed to do)
  - Protocol and behavior are complementary; this contract governs behavior boundaries
```

**Rationale:** Explicitly clarifies that E2E contract defines protocol, frontend contract defines behavior boundaries. They don't conflict, but the relationship should be explicit.
