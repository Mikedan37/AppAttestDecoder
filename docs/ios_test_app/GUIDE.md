# iOS Test App Guide

This guide describes the iOS test app for App Attest. The app is a diagnostic instrument that displays device-generated artifacts, forwards data to a backend, and records backend responses.

---

## Chapter 1: Introduction

### What This App Is

The iOS test app is a diagnostic instrument for observing App Attest flows. It displays:
- Data generated by the App Attest API
- Data sent to the backend
- Responses received from the backend
- Complete flow progression from key generation through assertion submission

### Purpose

This app records:
- Artifact generation (keys, attestations, assertions)
- Data transmission (request payloads, response payloads)
- Backend responses (status codes, response bodies)
- Flow trace (timestamps, state transitions)

Use this app to observe App Attest data flows, debug byte-level mismatches, and analyze artifact structure.

---

## Chapter 2: Frontend Operations

### Artifact Generation

The app calls Apple's App Attest API:
- `DCAppAttestService.generateKey()` → Returns keyID
- `DCAppAttestService.attestKey(keyID, clientDataHash:)` → Returns attestationObject
- `DCAppAttestService.generateAssertion(keyID, clientDataHash:)` → Returns assertionObject

Each operation returns bytes that the app displays and forwards unchanged to the backend.

### Data Transport

The app forwards exact bytes to the backend without modification. It handles network errors (connection failures, timeouts, HTTP errors) and displays error messages.

### Backend Response Display

The app displays backend HTTP responses verbatim. When the backend responds with status "verified" or "rejected", the app displays "Backend response (status: verified)" or "Backend response (status: rejected)" without interpretation.

### State Management

The app tracks flowID, keyID, and verifyRunID to maintain UI state. These checks maintain UI consistency.

---

## Chapter 3: Frontend Authority Boundaries

The frontend performs no cryptographic verification, makes no security decisions, treats responses as non-authoritative, and does not block operations based on backend status.

**No cryptographic verification:**
- No signature verification
- No certificate chain validation
- No certificate expiration checks
- No nonce verification

**No security decisions:**
- No trust decisions
- No authorization decisions
- No policy enforcement
- No validity interpretation

**Non-authoritative responses:**
- Backend responses are displayed verbatim
- Status values are literal strings, not interpreted
- No meaning is inferred from response codes

**No blocking:**
- Operations are not blocked based on backend status
- Buttons remain enabled regardless of response
- State is preserved regardless of response

## Chapter 4: Complete Flow

This chapter describes the UI flow from key generation through assertion submission.

### Step 1: Generate Key

**User action:** Tap "Generate Key"

**App behavior:**
- Calls `DCAppAttestService.generateKey()`
- Receives keyID (base64 string, 32 bytes when decoded)
- Displays keyID in UI
- Stores keyID for subsequent operations

**Displayed:** "Key ID: [base64 string]"

### Step 2: Attest Key

**User action:** Tap "Attest Key"

**App behavior:**
- Calls `DCAppAttestService.attestKey(keyID, clientDataHash:)`
- Receives attestationObject (CBOR bytes)
- Displays base64-encoded attestation
- Stores attestation for registration

**Displayed:** "Attestation Blob (base64): [base64 string]"

### Step 3: Register Attestation

**User action:** Tap "Register"

**App behavior:**
- Sends to backend:
  ```json
  {
    "keyID": "[base64]",
    "attestationObject": "[base64]",
    "challenge_base64": "[base64]"
  }
  ```
- Receives backend response
- Displays response verbatim
- Stores flowID if present in response

**Backend response example:**
```json
{
  "status": "accepted",
  "flowID": "123e4567-e89b-12d3-a456-426614174000"
}
```

**Displayed:** "Backend response (status: accepted): [full JSON]"

### Step 4: Request Challenge

**User action:** Tap "Get Challenge"

**App behavior:**
- Sends: `GET /app-attest/challenge?flowID=[uuid]&keyID=[base64]`
- Receives backend response
- Displays challenge information
- Stores challenge_id if present in response

**Backend response example:**
```json
{
  "challenge_b64": "[base64]",
  "challenge_id": "456e7890-e89b-12d3-a456-426614174001",
  "expiresAt": "2026-01-20T10:30:00Z"
}
```

**Displayed:** Challenge received, expiresAt shown

### Step 5: Generate Assertion

**User action:** Tap "Assert Key"

**App behavior:**
- Builds canonical clientData JSON with sorted keys
- Computes `clientDataHash = SHA256(clientDataBytes)`
- Calls `DCAppAttestService.generateAssertion(keyID, clientDataHash:)`
- Receives assertionObject (CBOR bytes)
- Displays assertion

**Displayed:** "Assertion Blob (base64): [base64 string]"

### Step 6: Send Assertion to Backend

**User action:** Tap "Send to Backend for Verification"

**App behavior:**
- Sends to backend:
  ```json
  {
    "keyID": "[base64]",
    "flowID": "[uuid]",
    "verifyRunID": "[uuid]",
    "challenge_id": "[uuid]",
    "clientData_base64": "[base64]",
    "assertionObject_base64": "[base64]"
  }
  ```
- Receives backend response
- Displays response verbatim
- Records response in flow trace

**Backend response example:**
```json
{
  "status": "verified"
}
```

**Displayed:** "Backend response (status: verified): [full JSON]"

### Flow Trace

The app records each step in a flow trace:

```
Diagnostic Flow Trace (no local verification performed)

Registration
  flowID: 123e4567-e89b-12d3-a456-426614174000
  Status: completed
  Details: keyID registered, flowID received

Challenge Request
  flowID: 123e4567-e89b-12d3-a456-426614174000
  Status: sent
  Details: verifyRunID: 789e0123-e89b-12d3-a456-426614174002

Challenge Received
  flowID: 123e4567-e89b-12d3-a456-426614174000
  Status: completed
  Details: challenge_id: 456e7890-e89b-12d3-a456-426614174001

Assertion Submission
  flowID: 123e4567-e89b-12d3-a456-426614174000
  Status: sent
  Details: verifyRunID: 789e0123-e89b-12d3-a456-426614174002

Backend Response
  flowID: 123e4567-e89b-12d3-a456-426614174000
  Status: verified
  Details: Backend returned status: verified
```

The flow trace records what happened, when it happened, and what the backend reported.

## Chapter 5: Examples

### Example 1: Complete Flow

**User actions:**
1. Tap "Generate Key"
2. Tap "Attest Key"
3. Tap "Register"
4. Tap "Get Challenge"
5. Tap "Assert Key"
6. Tap "Send to Backend for Verification"

**Data produced:**
- keyID: Base64 string (32 bytes decoded)
- attestationObject: CBOR bytes, base64-encoded
- clientDataBytes: Canonical JSON with sorted keys
- clientDataHash: SHA256(clientDataBytes), 32 bytes
- assertionObject: CBOR bytes, base64-encoded

**Data sent:**
- Registration: keyID, attestationObject, challenge_base64
- Challenge request: flowID, keyID (query parameters)
- Assertion submission: keyID, flowID, verifyRunID, challenge_id, clientData_base64, assertionObject_base64

**Backend response:**
```json
{
  "status": "verified"
}
```

**Displayed:** "Backend response (status: verified): [full JSON]"

### Example 2: Backend Rejection

**User actions:** Same as Example 1, through step 6

**Backend response:**
```json
{
  "status": "rejected",
  "reason": "ECDSA_VERIFY_FAILED"
}
```

**Displayed:** "Backend response (status: rejected): [full JSON]"

**UI state:**
- All buttons remain enabled
- State (flowID, keyID, assertion) remains available
- User can generate new assertion
- User can send assertion again
- User can continue using the app

**Flow trace entry:**
```
Backend Response
  flowID: 123e4567-e89b-12d3-a456-426614174000
  Status: rejected
  Details: Backend returned status: rejected
```

### Example 3: Repeated Submission

**User actions:**
1. Complete flow as in Example 1
2. Tap "Send to Backend for Verification" again (without generating new assertion)

**Data sent:**
- Same assertionObject_base64 as previous submission
- Same clientData_base64 as previous submission
- Same flowID
- New verifyRunID for this submission

**Backend response:**
```json
{
  "status": "rejected",
  "reason": "REPLAY_DETECTED"
}
```

**Displayed:** "Backend response (status: rejected): [full JSON]"

**UI state:**
- All functionality remains available
- No blocking or prevention of repeated submissions

## Chapter 6: Setup and Usage

### Prerequisites

- Physical Apple device (iPhone or iPad running iOS 14.0 or later)
- Apple Developer Account (free or paid)
- Xcode (14.0 or later)
- App Attest capability enabled for your App ID

**Note:** App Attest does not work on simulators. A physical device is required.

### Apple Developer Setup

1. Create an App ID in Apple Developer Portal
2. Enable "App Attest" capability for the App ID
3. Note your Bundle ID (e.g., `com.example.AppAttestDecoderTestApp`)

### Xcode Configuration

1. Open `AppAttestDecoderCLI.xcodeproj` in Xcode
2. Select the `AppAttestDecoderTestApp` target
3. Set Bundle Identifier to match your App ID
4. Ensure "App Attest" capability is enabled in Signing & Capabilities

### Local Network Configuration

The test app communicates with a backend server. Configure local network access:

**iOS Settings:**
1. Settings → Privacy & Security → Local Network
2. Enable access for `AppAttestDecoderTestApp`

**App Transport Security:**
The test app uses HTTP for local development. Ensure ATS allows local network access or add an exception for your backend IP address.

See `IOS_SANDBOX_SETUP.md` for detailed configuration.

### Backend Configuration

1. Launch the app
2. Enter backend URL (e.g., `http://10.0.0.108:8080`)
3. Use "Ping Backend" button to verify connectivity

### Running the App

1. Connect physical device to Mac
2. Select device in Xcode
3. Build and run (Cmd+R)
4. Follow the flow: Generate Key → Attest Key → Register → Assert Key → Send to Backend

## Chapter 7: Testing and Verification

This chapter describes how to verify that the frontend displays data and records responses without making security decisions.

### Code Examination

**Search for verification calls:**
- `isValidSignature` → Should find 0 results
- `verifySignature` → Should find 0 results
- `CryptoKit.*verify` → Should find 0 results

**Search for backend attribution:**
- `Backend response` → Should find all response displays
- `Backend returned status` → Should find status attribution

**Search for state-based errors:**
- `flowID missing` → Should find state errors
- `keyID mismatch` → Should find state consistency checks

**Search for blocking logic:**
- `disabled.*backend` → Should find 0 results
- `if.*rejected.*disabled` → Should find 0 results

### Test Checklist

**Test 1: Backend Response Display**

Complete full flow and observe backend response display. Verify:
- Response text matches exactly what backend sent
- UI shows "Backend response (status: verified)" or "Backend response (status: rejected)"
- No frontend interpretation or modification of response text
- Console logs show raw backend response JSON

**Test 2: No Blocking Based on Backend Response**

When backend returns "rejected", verify:
- Buttons remain enabled
- New assertions can be generated with the same keyID
- Assertions can be sent multiple times
- No UI blocking or disabling occurs based on backend status

**Test 3: No Local Security Decisions**

Check console logs for any security-related decisions. Verify:
- No local signature verification
- No certificate chain validation
- No policy enforcement
- Only state consistency checks (keyID matches, flowID exists)

**Test 4: Flow Trace Observability**

Complete full flow and open Flow Trace view. Verify:
- Flow trace shows all steps with timestamps
- flowID displayed for each step
- Status shows "completed", "sent", "verified", or "rejected"
- Labeled as "Diagnostic Flow Trace. No local verification performed"

**Test 5: Error Messages Are State-Based**

Attempt operations out of order (e.g., send assertion without completing registration). Verify:
- Error messages describe state issues ("flowID missing", "keyID mismatch")
- No security language ("invalid", "unauthorized", "blocked")
- Messages clarify what state is needed

See `FRONTEND_NON_AUTHORITY_TEST.md` for detailed test procedures with code references.

## Chapter 8: Troubleshooting

### Network Connectivity

**Backend Not Reachable**

Symptoms: "Ping Backend" fails, HTTP errors, local network permission errors.

Solutions:
- Verify backend is running
- Check local network permissions (Settings → Privacy & Security → Local Network)
- Verify backend URL is correct
- Check App Transport Security configuration

**URL Encoding Issues**

Symptoms: Backend returns "flowID and keyID query parameters required" or "Invalid keyID format".

Solutions:
- Frontend uses `URLComponents` and `URLQueryItem` for encoding
- keyID is base64-encoded using custom encoding for `+`, `/`, `=`
- Check frontend logs for `percentEncodedQuery` value

### App Attest Capability

**"App Attest Not Available"**

Symptoms: Error when calling `DCAppAttestService.shared.isSupported` or when generating keys.

Solutions:
- Verify capability is enabled in Xcode (Signing & Capabilities)
- Verify App ID configuration in Apple Developer Portal
- Use physical device (App Attest does not work on simulators)

**Key Generation Fails**

Symptoms: `generateKey()` returns error, key generation button does nothing.

Solutions:
- Check device logs for specific error
- Ensure device has Secure Enclave (iPhone 5s or later)
- Ensure device is not in a restricted state

### State Consistency

**"flowID is missing"**

Symptoms: Cannot proceed past Register step, challenge request fails.

Solutions:
- Ensure Register completed successfully
- Check backend response contains flowID
- If Register failed, try again with new key

**"keyID mismatch"**

Symptoms: Verify request fails with keyID mismatch error.

Solutions:
- Do not generate new key mid-flow
- If key changed, restart flow: Generate Key → Attest → Register → Assert → Verify
- Check UI shows correct registered keyID

**"Missing assertion evidence"**

Symptoms: Cannot send assertion to backend, evidence store is empty.

Solutions:
- Ensure "Assert Key" completed successfully
- Check logs for assertion generation errors
- Try generating assertion again

### Backend Errors

**"challenge_base64 required"**

Symptoms: Register request fails, backend returns error about missing challenge.

Solutions:
- Complete "Attest Key" step before attempting Register
- Check `ClientDataContext` contains challenge
- Verify challenge is base64-encoded correctly

**"Invalid challenge response"**

Symptoms: Challenge request succeeds but assertion generation fails.

Solutions:
- Check backend logs for challenge validation
- Verify challenge decodes to 32 bytes
- Ensure challenge_id is valid UUID

**"ECDSA verification failed"**

Symptoms: Backend returns verification failure, backend reports signature mismatch.

Solutions:
- This is a backend verification issue, not frontend
- Check backend logs for detailed error
- Verify `clientData_base64` matches what backend expects
- Check `signedBytes` computation matches backend

### UI Issues

**Buttons Disabled**

Symptoms: Buttons grayed out during operations, cannot proceed to next step.

Solutions:
- Wait for current operation to complete
- Check for error messages
- Verify network connectivity

**No Response Displayed**

Symptoms: Backend request completes but no response shown, UI does not update.

Solutions:
- Check console logs for errors
- Verify response decoding succeeds
- Check UI state updates on main thread

### Finding Logs

All logs are prefixed with:
- `[ContentView]` - Main view operations
- `[FRONTEND]` - Frontend-specific logs
- `verifyRunID=...` - Correlation ID for full flow

Common log patterns:
- Registration: `[ContentView] REGISTER PRE-FLIGHT: ...`
- Challenge: `[FRONTEND][CHALLENGE][REQUEST] ...`
- Verify: `[ContentView] VERIFY verifyRunID=... | ...`
