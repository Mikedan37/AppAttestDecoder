# iOS Test App Guide

This guide explains how to understand and use the iOS test app for App Attest. The app is a diagnostic tool that generates artifacts, transports data, and displays backend responses. It does not perform verification or make security decisions.

---

## Chapter 1: Introduction

### What This App Is

The iOS test app is a diagnostic tool for learning and debugging App Attest implementations. It demonstrates how a frontend generates artifacts using Apple's App Attest API, sends them to a backend, and displays responses.

The app shows:
- What data is generated by the App Attest API
- What data is sent to the backend
- What responses are received from the backend
- How the complete flow progresses from key generation through assertion submission

### What This App Is Not

This app is not a production client, security component, or verification tool. It does not:
- Verify cryptographic signatures
- Make trust or authorization decisions
- Enforce security policies
- Block operations based on backend responses

All verification and security decisions are made by the backend. The frontend only generates, transports, and displays data.

### Purpose

Use this app to:
- Learn how App Attest data flows work
- Debug byte-level mismatches between frontend and backend
- Test backend integration during development
- Analyze artifact structure for forensics

Do not use this app to:
- Make security decisions
- Validate production systems
- Authorize users or operations
- Prove compliance or security

## Chapter 2: Understanding the Frontend

### Responsibilities

The frontend has four main responsibilities:

**1. Generate Artifacts**

The app calls Apple's App Attest API to create:
- Keys via `DCAppAttestService.generateKey()`
- Attestations via `DCAppAttestService.attestKey()`
- Assertions via `DCAppAttestService.generateAssertion()`

Each operation returns bytes that the app displays and sends unchanged to the backend.

**2. Transport Data**

The app sends exact bytes to the backend without modification. It handles network errors (connection failures, timeouts, HTTP errors) but does not interpret the meaning of responses.

**3. Display Backend Responses**

The app shows backend HTTP responses verbatim. It attributes status to the backend ("Backend response (status: verified)") and does not infer meaning from response codes.

**4. Maintain State for UI Consistency**

The app tracks flowID, keyID, and verifyRunID to maintain UI state. These checks ensure UI consistency, not security.

### Non-Responsibilities

The frontend does not:
- Verify cryptographic signatures
- Validate certificate chains
- Check certificate expiration or revocation
- Make trust decisions
- Enforce policies
- Block operations based on backend status

All verification and security decisions are the backend's responsibility.

### Security Boundary

The frontend operates on the client side of a security boundary. The backend operates on the server side where all cryptographic verification happens.

**Frontend responsibility:** Generate and transport artifacts correctly.

**Backend responsibility:** Verify cryptographic signatures, validate certificate chains, enforce policies, prevent replay attacks.

## Chapter 3: Observing App Attest

### What Can Be Observed

The app records what happens during App Attest operations:

**Artifact Generation**
- keyID returned by the App Attest API
- attestationObject bytes returned by the API
- assertionObject bytes returned by the API
- Timestamps for each operation

**Data Flow**
- Exact bytes sent to backend
- Exact bytes received from backend
- State transitions (flowID, challenge_id, verifyRunID changes)
- HTTP status codes and response times

**Byte-Level Evidence**
- Raw bytes extracted from artifacts (authenticatorData, signature, certificates)
- SHA256 hashes computed for log correlation
- Base64 encoding/decoding behavior
- CBOR and ASN.1 structure decoded for logging

**Backend Communication**
- Request payloads sent to backend
- Response payloads received from backend
- HTTP status codes
- Backend error messages verbatim

**Flow Trace**
- Complete flow from registration through assertion submission
- Timestamps for each step
- flowID continuity across steps
- Backend response status (recorded without interpretation)

### What Cannot Be Proved

The app cannot prove:
- Cryptographic validity (signatures, certificate chains, nonces)
- Security properties (authenticity, replay protection, policy enforcement)
- Trust decisions (whether keys should be trusted, assertions accepted, users authorized)
- Correctness guarantees (implementation correctness, protocol compliance, production readiness)

**Reason:** The frontend does not perform cryptographic verification. All verification happens on the backend. This is a diagnostic test app for observation and learning only.

### Measurement vs Security

**This app measures:**
- What data is generated (artifact bytes, hashes, structure)
- What data is sent (request payloads, encoding)
- What data is received (response payloads, status codes)
- When operations occur (timestamps, flow sequence)
- How state changes (flowID, challenge_id, verifyRunID transitions)

**This app does not measure:**
- Whether data is valid (backend's responsibility)
- Whether operations are secure (backend's responsibility)
- Whether decisions are correct (backend's responsibility)
- Whether policy is enforced (backend's responsibility)

## Chapter 4: Complete Flow

This chapter walks through a complete App Attest flow from key generation through assertion submission.

### Step 1: Generate Key

The app calls `DCAppAttestService.generateKey()` and receives a keyID (base64 string, 32 bytes when decoded). The app displays the keyID and stores it for subsequent operations.

**What the app does:** Calls API, receives keyID, displays it.

**What the app does not decide:** Whether the key is valid or secure.

### Step 2: Attest Key

The app calls `DCAppAttestService.attestKey(keyID, clientDataHash:)` and receives an attestationObject (CBOR bytes). The app displays the base64-encoded attestation and stores it for registration.

**What the app does:** Calls API, receives attestation bytes, displays them.

**What the app does not decide:** Whether the attestation is valid or trustworthy.

### Step 3: Register Attestation

The app sends to the backend:
```json
{
  "keyID": "[base64]",
  "attestationObject": "[base64]",
  "challenge_base64": "[base64]"
}
```

The backend responds with:
```json
{
  "status": "accepted",
  "flowID": "123e4567-e89b-12d3-a456-426614174000"
}
```

The app displays "Backend response (status: accepted): [full JSON]" and stores the flowID for subsequent requests.

**What the app does:** Sends registration data, receives flowID, stores it.

**What the app does not decide:** Whether registration should succeed or fail.

### Step 4: Request Challenge

The app sends:
```
GET /app-attest/challenge?flowID=[uuid]&keyID=[base64]
```

The backend responds with:
```json
{
  "challenge_b64": "[base64]",
  "challenge_id": "456e7890-e89b-12d3-a456-426614174001",
  "expiresAt": "2026-01-20T10:30:00Z"
}
```

The app displays the challenge information and stores challenge_id for assertion submission.

**What the app does:** Requests challenge, receives challenge data, stores challenge_id.

**What the app does not decide:** Whether the challenge is valid or expired.

### Step 5: Generate Assertion

The app builds canonical clientData JSON with sorted keys, computes `clientDataHash = SHA256(clientDataBytes)`, and calls `DCAppAttestService.generateAssertion(keyID, clientDataHash:)`. The app receives an assertionObject (CBOR bytes) and displays it.

**What the app does:** Builds clientData, computes hash, calls API, receives assertion bytes.

**What the app does not decide:** Whether the assertion will verify or is correct.

### Step 6: Send Assertion to Backend

The app sends:
```json
{
  "keyID": "[base64]",
  "flowID": "[uuid]",
  "verifyRunID": "[uuid]",
  "challenge_id": "[uuid]",
  "clientData_base64": "[base64]",
  "assertionObject_base64": "[base64]"
}
```

The backend responds with:
```json
{
  "status": "verified"
}
```

The app displays "Backend response (status: verified): [full JSON]" and records the response in the flow trace.

**What the app does:** Sends assertion data, receives backend response, displays it verbatim.

**What the app does not decide:** Whether verification should succeed or fail.

### Flow Trace

The app records each step in a flow trace:

```
Diagnostic Flow Trace (no local verification performed)

Registration
  flowID: 123e4567-e89b-12d3-a456-426614174000
  Status: completed
  Details: keyID registered, flowID received

Challenge Request
  flowID: 123e4567-e89b-12d3-a456-426614174000
  Status: sent
  Details: verifyRunID: 789e0123-e89b-12d3-a456-426614174002

Challenge Received
  flowID: 123e4567-e89b-12d3-a456-426614174000
  Status: completed
  Details: challenge_id: 456e7890-e89b-12d3-a456-426614174001

Assertion Submission
  flowID: 123e4567-e89b-12d3-a456-426614174000
  Status: sent
  Details: verifyRunID: 789e0123-e89b-12d3-a456-426614174002

Backend Response
  flowID: 123e4567-e89b-12d3-a456-426614174000
  Status: verified
  Details: Backend returned status: verified
```

The flow trace shows what happened, when it happened, and what the backend reported. It does not interpret or verify anything.

## Chapter 5: Examples

This chapter presents concrete examples of different scenarios.

### Example 1: Successful Flow

A complete end-to-end flow where all steps succeed.

**Flow Sequence:**

1. Generate Key → keyID received
2. Attest Key → attestationObject received
3. Register Attestation → flowID received
4. Request Challenge → challenge received
5. Generate Assertion → assertionObject received
6. Send Assertion → Backend responds with status "verified"

**What the App Produced:**
- keyID: Base64 string (32 bytes decoded)
- attestationObject: CBOR bytes, base64-encoded
- clientDataBytes: Canonical JSON with sorted keys
- clientDataHash: SHA256(clientDataBytes), 32 bytes
- assertionObject: CBOR bytes, base64-encoded

**What the App Sent:**
- Registration: keyID, attestationObject, challenge_base64
- Challenge request: flowID, keyID (query parameters)
- Assertion submission: keyID, flowID, verifyRunID, challenge_id, clientData_base64, assertionObject_base64

**What the App Displayed:**
- Backend responses verbatim (no modification)
- State information (flowID, challenge_id, verifyRunID)
- Timestamps for flow trace
- Error messages describing state issues, not security

**What the App Did Not Decide:**
- Whether key generation succeeded (API returned keyID)
- Whether attestation is valid (API returned bytes)
- Whether registration should succeed (backend decision)
- Whether challenge is valid (backend decision)
- Whether assertion will verify (backend decision)
- Whether verification should succeed (backend decision)

### Example 2: Backend Rejection

A flow where the backend rejects the assertion.

**Flow Sequence:**

1. Generate Key → Success
2. Attest Key → Success
3. Register Attestation → Success
4. Request Challenge → Success
5. Generate Assertion → Success
6. Send Assertion → Backend responds with status "rejected"

**Backend Response:**
```json
{
  "status": "rejected",
  "reason": "ECDSA_VERIFY_FAILED"
}
```

**What the App Does:**

- Displays: "Backend response (status: rejected): [full JSON]"
- Logs: Backend response verbatim to console
- Records: Flow trace entry with status "rejected"
- Maintains: All UI buttons remain enabled
- Preserves: State (flowID, keyID, assertion) remains available

**What the App Does Not Do:**

- Does not disable buttons
- Does not clear state
- Does not prevent generating new assertions
- Does not block sending assertions again
- Does not interpret "rejected" as a security decision
- Does not make any trust or authorization decisions

**User Can Still:**

- Generate new assertion with same keyID
- Send assertion again (if backend allows)
- Continue using the app
- View flow trace
- Copy evidence bundles
- Inspect artifacts

### Example 3: Repeated Submission

A scenario where the same assertion is sent twice.

**Flow Sequence:**

1. Complete successful flow (as in Example 1)
2. Send same assertion again (without generating new assertion)

**What the App Does:**

- Sends same assertionObject_base64 again
- Sends same clientData_base64 again
- Uses same flowID
- Generates new verifyRunID for this submission
- Displays backend response verbatim

**What the App Does Not Do:**

- Does not prevent sending same assertion twice
- Does not check if assertion was already used
- Does not enforce replay protection
- Does not decide whether replay is allowed

**Backend Response (Replay Scenario):**
```json
{
  "status": "rejected",
  "reason": "REPLAY_DETECTED"
}
```

**What the App Does:**

- Displays: "Backend response (status: rejected): [full JSON]"
- Records: Flow trace entry with status "rejected"
- Maintains: All functionality available

**What the App Does Not Do:**

- Does not prevent replay (backend enforces)
- Does not interpret rejection reason
- Does not make security decisions about replay

## Chapter 6: Setup and Usage

### Prerequisites

- Physical Apple device (iPhone or iPad running iOS 14.0 or later)
- Apple Developer Account (free or paid)
- Xcode (14.0 or later)
- App Attest capability enabled for your App ID

**Note:** App Attest does not work on simulators. A physical device is required.

### Apple Developer Setup

1. Create an App ID in Apple Developer Portal
2. Enable "App Attest" capability for the App ID
3. Note your Bundle ID (e.g., `com.example.AppAttestDecoderTestApp`)

### Xcode Configuration

1. Open `AppAttestDecoderCLI.xcodeproj` in Xcode
2. Select the `AppAttestDecoderTestApp` target
3. Set Bundle Identifier to match your App ID
4. Ensure "App Attest" capability is enabled in Signing & Capabilities

### Local Network Configuration

The test app communicates with a backend server. Configure local network access:

**iOS Settings:**
1. Settings → Privacy & Security → Local Network
2. Enable access for `AppAttestDecoderTestApp`

**App Transport Security:**
The test app uses HTTP for local development. Ensure ATS allows local network access or add an exception for your backend IP address.

See `IOS_SANDBOX_SETUP.md` for detailed configuration.

### Backend Configuration

1. Launch the app
2. Enter backend URL (e.g., `http://10.0.0.108:8080`)
3. Use "Ping Backend" button to verify connectivity

### Running the App

1. Connect physical device to Mac
2. Select device in Xcode
3. Build and run (Cmd+R)
4. Follow the flow: Generate Key → Attest Key → Register → Assert Key → Send to Backend

## Chapter 7: Testing and Verification

This chapter explains how to verify that the frontend makes no security decisions and attributes all verification to the backend.

### Quick Review (Without Running App)

You can verify non-authority by examining the code:

**Search for verification calls:**
- `isValidSignature` → Should find 0 results
- `verifySignature` → Should find 0 results
- `CryptoKit.*verify` → Should find 0 results

**Search for backend attribution:**
- `Backend response` → Should find all response displays
- `Backend returned status` → Should find status attribution
- `backend performs` → Should find verification attribution

**Search for state-based errors:**
- `flowID missing` → Should find state errors, not security errors
- `keyID mismatch` → Should find state consistency checks
- `state error` → Should find state-based language

**Search for blocking logic:**
- `disabled.*backend` → Should find 0 results
- `if.*rejected.*disabled` → Should find 0 results
- `if.*verified.*enabled` → Should find 0 results

### Test Checklist

**Test 1: Backend Response Display**

Complete full flow and observe backend response display. Verify:
- Response text matches exactly what backend sent
- UI shows "Backend response (status: verified)" or "Backend response (status: rejected)"
- No frontend interpretation or modification of response text
- Console logs show raw backend response JSON

**Test 2: No Blocking Based on Backend Response**

When backend returns "rejected", verify:
- Buttons remain enabled
- New assertions can be generated with the same keyID
- Assertions can be sent multiple times
- No UI blocking or disabling occurs based on backend status

**Test 3: No Local Security Decisions**

Check console logs for any security-related decisions. Verify:
- No local signature verification
- No certificate chain validation
- No policy enforcement (bundle ID, environment)
- No trust decisions
- Only state consistency checks (keyID matches, flowID exists)

**Test 4: Flow Trace Observability**

Complete full flow and open Flow Trace view. Verify:
- Flow trace shows all steps with timestamps
- flowID displayed for each step
- Status shows "completed", "sent", "verified", or "rejected"
- No security language or interpretation
- Labeled as "Diagnostic Flow Trace. No local verification performed"

**Test 5: Error Messages Are State-Based**

Attempt operations out of order (e.g., send assertion without completing registration). Verify:
- Error messages describe state issues ("flowID missing", "keyID mismatch")
- No security language ("invalid", "unauthorized", "blocked")
- Messages clarify what state is needed, not why it's needed

See `FRONTEND_NON_AUTHORITY_TEST.md` for detailed test procedures with code references.

## Chapter 8: Troubleshooting

### Network Connectivity

**Backend Not Reachable**

Symptoms: "Ping Backend" fails, HTTP errors, local network permission errors.

Solutions:
- Verify backend is running
- Check local network permissions (Settings → Privacy & Security → Local Network)
- Verify backend URL is correct
- Check App Transport Security configuration

**URL Encoding Issues**

Symptoms: Backend returns "flowID and keyID query parameters required" or "Invalid keyID format".

Solutions:
- Frontend uses `URLComponents` and `URLQueryItem` for encoding
- keyID is base64-encoded using custom encoding for `+`, `/`, `=`
- Check frontend logs for `percentEncodedQuery` value

### App Attest Capability

**"App Attest Not Available"**

Symptoms: Error when calling `DCAppAttestService.shared.isSupported` or when generating keys.

Solutions:
- Verify capability is enabled in Xcode (Signing & Capabilities)
- Verify App ID configuration in Apple Developer Portal
- Use physical device (App Attest does not work on simulators)

**Key Generation Fails**

Symptoms: `generateKey()` returns error, key generation button does nothing.

Solutions:
- Check device logs for specific error
- Ensure device has Secure Enclave (iPhone 5s or later)
- Ensure device is not in a restricted state

### State Consistency

**"flowID is missing"**

Symptoms: Cannot proceed past Register step, challenge request fails.

Solutions:
- Ensure Register completed successfully
- Check backend response contains flowID
- If Register failed, try again with new key

**"keyID mismatch"**

Symptoms: Verify request fails with keyID mismatch error.

Solutions:
- Do not generate new key mid-flow
- If key changed, restart flow: Generate Key → Attest → Register → Assert → Verify
- Check UI shows correct registered keyID

**"Missing assertion evidence"**

Symptoms: Cannot send assertion to backend, evidence store is empty.

Solutions:
- Ensure "Assert Key" completed successfully
- Check logs for assertion generation errors
- Try generating assertion again

### Backend Errors

**"challenge_base64 required"**

Symptoms: Register request fails, backend returns error about missing challenge.

Solutions:
- Complete "Attest Key" step before attempting Register
- Check `ClientDataContext` contains challenge
- Verify challenge is base64-encoded correctly

**"Invalid challenge response"**

Symptoms: Challenge request succeeds but assertion generation fails.

Solutions:
- Check backend logs for challenge validation
- Verify challenge decodes to 32 bytes
- Ensure challenge_id is valid UUID

**"ECDSA verification failed"**

Symptoms: Backend returns verification failure, backend reports signature mismatch.

Solutions:
- This is a backend verification issue, not frontend
- Check backend logs for detailed error
- Verify `clientData_base64` matches what backend expects
- Check `signedBytes` computation matches backend

### UI Issues

**Buttons Disabled**

Symptoms: Buttons grayed out during operations, cannot proceed to next step.

Solutions:
- Wait for current operation to complete
- Check for error messages
- Verify network connectivity

**No Response Displayed**

Symptoms: Backend request completes but no response shown, UI does not update.

Solutions:
- Check console logs for errors
- Verify response decoding succeeds
- Check UI state updates on main thread

### Finding Logs

All logs are prefixed with:
- `[ContentView]` - Main view operations
- `[FRONTEND]` - Frontend-specific logs
- `verifyRunID=...` - Correlation ID for full flow

Common log patterns:
- Registration: `[ContentView] REGISTER PRE-FLIGHT: ...`
- Challenge: `[FRONTEND][CHALLENGE][REQUEST] ...`
- Verify: `[ContentView] VERIFY verifyRunID=... | ...`

The iOS test app is a diagnostic tool that demonstrates App Attest data flow. It generates artifacts, transports data unchanged to the backend, and displays backend responses verbatim. It does not perform verification or make security decisions.
