# App Attest End-to-End Contract

Single, unambiguous contract for the iOS test app and backend. No alternate paths. Identity continuity is enforced by binding rules.

**Ownership:** Backend owns freshness, binding enforcement, replay protection, and verification. Frontend generates artifacts and logs evidence only; makes no trust decisions.

## The One True Flow

| Step | Actor | Action |
|------|-------|--------|
| **0** | Device | Generate Key: `keyID = DCAppAttestService.generateKey()`. Store in app state. Do not regenerate mid-run. |
| **1** | Device | Attest Key: `attestationObject = attestKey(keyID, clientDataHash: <...>)` |
| **2** | Backend | **Register**: Frontend sends `{ keyID, attestationObject }`. Backend decodes, extracts public key, stores `keyID → publicKey`, returns `{ flowID }`. |
| **3** | Backend | **Get Client Data Hash**: Frontend sends `{ keyID, flowID, verifyRunID }`. Backend builds clientDataJSON, `clientDataHash = SHA256(clientDataJSON)`, stores under flowID, returns `{ clientDataHash, expiresAt }` (and optionally `verifyRunID`). |
| **4** | Device | **Generate Assertion**: `assertionObject = generateAssertion(keyID, clientDataHash: <from step 3>)`. Frontend never computes clientDataHash for this path. |
| **5** | Backend | **Verify**: Frontend sends `{ keyID, flowID, verifyRunID, assertionObject }`. Backend loads `clientDataHash` by flowID, `publicKey` by keyID, decodes assertion → authenticatorData + signature, verifies. |

**Button order (enforced in UI):** Generate Key → Attest → Register → Assert Key (Get ClientDataHash + Generate Assertion) → Verify.

---

## Three Hard Bindings

If any binding is violated, verification is invalid. Backend must enforce.

### Binding A: flowID ↔ keyID

When a flow is created at Register, it is tied to that keyID.

- **Rule:** Reject `/client-data-hash` or `/verify` if `flowID.keyID != request.keyID`.

### Binding B: flowID ↔ clientDataHash

clientDataHash is stored only under flowID. Not “latest for key,” not global.

- **Rule:** Reject `/verify` if clientDataHash is missing or expired for that flowID.

### Binding C: keyID ↔ publicKey

Public key must be stable for the full run.

- **Rule:** If the backend restarts and loses in-memory store, frontend must re-register. Backend **must** persist `keyID → publicKey` (e.g. on disk) or clearly document that restart requires re-register.

## What the Frontend Sends

| Request | Body |
|---------|------|
| **POST /app-attest/register** | `{ keyID, attestationObject }` |
| **POST /app-attest/client-data-hash** | `{ keyID, flowID, verifyRunID }` |
| **POST /app-attest/verify** | `{ keyID, flowID, verifyRunID, assertionObject }` |

- **verifyRunID:** Generated by frontend at the start of each client-data-hash request. Backend **must** log it and store on the flow. One grep reconstructs the full chain.
- **keyID** is sent with verify even when flowID exists; backend checks Binding A.

---

## What the Backend Must Do

### Storage

Persist (or accept re-register after restart):

- `keyID → publicKeyX963`
- `flowID → { keyID, clientDataHash, expiresAt, status, verifyRunID? }`

### Verify Handler

1. Base64-decode `assertionObject` once.
2. Decode CBOR → `authenticatorData`, `signature`.
3. Load `clientDataHash` from flow store (by flowID).
4. Load `publicKey` from key store (by keyID).
5. Check Binding A (flowID.keyID == request.keyID) and Binding B (clientDataHash present, not expired).
6. Compute `signedBytes = authenticatorData || clientDataHash` from raw bytes.
7. Verify signature over `signedBytes` with `publicKey`.

### SIX_VALUES

Backend **must** emit the same six values as the frontend, keyed by flowID and verifyRunID:

- `verifyRunID`
- `authenticatorData.sha256`
- `clientDataHash.sha256`
- `signedBytes.sha256`
- `signature.sha256`
- `keyID_sha256`

Use `docs/SIX_VALUES_PROCEDURE.md` to compare frontend vs backend when verification fails.

## FlowID: When It Starts

**Option 1 (this app):** flowID starts at Register. REGISTER returns flowID; that flowID is used for client-data-hash and verify.

**Option 2 (stricter):** flow starts before Attest; `/begin-flow` returns flowID + clientDataHash for attestation; register uses same flowID. More moving pieces; Option 1 is sufficient for this test harness.

---

## Frontend Rules (Already Enforced)

The iOS test app is a **reference frontend only**—not a production client; intentionally verbose, forensic, and non-optimized.

- **Single-flight:** Buttons disabled during in-flight requests.
- **No key regeneration mid-flow:** If keyID changes (Generate Key), clear flowID, registeredKeyID, currentVerifyRunID, pending assertion state.
- **No clientDataHash on device for verify path:** Frontend uses only backend-provided clientDataHash for `generateAssertion`.
- **Always send flowID** with client-data-hash and verify (after Register).
- **Always send keyID** with verify.
- **Always send verifyRunID** with client-data-hash and verify.
